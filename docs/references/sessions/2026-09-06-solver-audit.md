# Session record — 2026-09-06 — solver audit and MSC Irina re-run

Reference record of what was measured on 2026-09-06, and at which commit. Raw console
output is under `docs/plans/benchmarks/v0.3.0-regen/`. `PAPER.md` §6–§7 is to be
rewritten from this record.

The session began as an accuracy audit of the nine open GitHub issues and turned into
a solver audit: three defects were found, each of which invalidates every benchmark
figure published before it.

## Defects found

### D-1 — The solver was planning in four dimensions ([#16](https://github.com/AlexanderSlokov/kuberina/issues/16), fixed in `93993c6`)

`gen_irina_testdata.py` emitted throughput flat (`disk_read`, `net_in`) while IR
v0.2.0 nests it under `disk` and `network`. `RawResources` did not deny unknown
fields, so `serde` discarded all four keys: pod I/O demand parsed as 0, node I/O
capacity fell through to the `f64::MAX` unconstrained default.

Caught by `inspector/`, which shares no code with the solver and therefore read the
keys the file actually contained. Both independent verifiers agreed to the unit
against a solution the solver had scored at zero capacity penalty:

| Dimension  | Solver | Inspector  | `mathematical_proof.py` |
|------------|--------|------------|-------------------------|
| disk_read  | 0      | 48,959.00  | 48,959.00               |
| disk_write | 0      | 122,102.00 | 122,102.00              |
| net_in     | 0      | 311,700.00 | 311,700.00              |
| net_out    | 0      | 345,415.00 | 345,415.00              |

### D-2 — FFD ordered by raw magnitude ([#18](https://github.com/AlexanderSlokov/kuberina/issues/18), fixed in `1ab1ad7`)

`synthetic_volume` summed CPU cores, GiB and MB/s directly, compensating with I/O
weights of 0.01 against 1.0 for CPU. The I/O-heavy pods sorted last and 15 of them
reached the fallback in `ffd_warmstart` that overloads a node without recording it —
all 15 onto `mem-000`, the first node matching their `disk: nvme` selector.

Reproduced in Python against the same data, both orderings:

| Configuration | Ordering                | Fallback | Overflow  | Active |
|---------------|-------------------------|----------|-----------|--------|
| Full packing  | `FfdWeights::default()` | 0        | 0.00      | 540    |
| Full packing  | normalized-max          | 0        | 0.00      | 540    |
| 20% headroom  | `FfdWeights::default()` | 15       | 41,166.80 | 581    |
| 20% headroom  | normalized-max          | 0        | **0.00**  | 610    |

The 581 matches the Rust solver, which confirms the replica.

**The instance was never infeasible** — a plain first-fit-decreasing places all 2,714 pods at 20%
headroom with zero overflow. Verified independently: every pod fits at least one
eligible node at 80%, and the tightest dimension across all three nodeSelector
classes uses 51.1% of reserved supply.

### D-3 — The GA never searched ([#19](https://github.com/AlexanderSlokov/kuberina/issues/19), fixed in `1ab1ad7`)

`init_population` perturbed at rate 0.2 and `mutate` at 0.03, both per-gene, on a
2,714-gene chromosome — ~543 random relocations per initial individual and ~81 per
child. No offspring landed near its parent; elitism preserved the FFD seed unchanged.

Both configurations early-stopped at generation 199 with final fitness identical to
the seed to four decimals: 1582583.1142 (full packing) and 414402512.4033 (20%
headroom). The 20% headroom seed is 15 single-pod relocations from 99% less overflow,
and the GA returned it untouched.

| Reserved (20%) | 441   | 615 / 441 = **1.3946** |

**1.3946 is the comparable figure.** It is the only model in which numerator and
denominator saw the same cluster: the solver placed pods into 80% of capacity, so
the bound it should be judged against is the one computed from 80% of capacity.
1.7422 divides a reserved-capacity result by a real-capacity bound and is reported
only to make that mismatch visible — #8 exists because the script used to report
that number alone.

Monte Carlo is instance-level, not configuration-level, so it repeats the
full-packing figures exactly: 699.7 ± 18.6 random uniform, 439.4 ± 15.9
selector-aware, best trial 379, Kuberina 0, `p < 1.0 × 10⁻⁴`.

The GA contributed 0.0014% here — 2,305,971.13 to 2,305,938.08 over 1,000
generations, all of it utilization variance (0.0647 → 0.0383). Active nodes never
moved off 615, from generation 0 to generation 1,000. Reserving 20% raises the
per-node ceiling the FFD seed packs against, so the seed already spreads across
nearly every node and there is no node the GA can empty by relocating pods one at a
time. This is the same structural limitation as the full-packing run, more visible
because the seed leaves less slack.

### Side by side

| Metric                  | Full packing | 20% headroom |
|-------------------------|--------------|--------------|
| Active nodes            | 539 / 620    | 615 / 620    |
| Empty nodes             | 81           | 5            |
| Avg CPU utilization     | 29.6%        | 25.0%        |
| Fragmentation (vs real) | 1,567,313.50 | 3,265,407.50 |
| Fragmentation (as scored)| 1,567,313.50 | 2,299,752.00 |
| Utilization variance    | 0.0537       | 0.0383       |
| Capacity overflow       | 0            | 0            |
| α (matched model)       | 1.5269       | 1.3946       |
| GA gain over FFD seed   | 0.62%        | 0.0014%      |
| Wall clock              | 912.49 s     | 895.07 s     |

Reserving 20% costs 76 nodes and buys a flatter cluster: variance falls, no node
exceeds 77% CPU, and every dimension stays inside real capacity with a fifth of it
untouched. The two α values are not comparable to each other — each is measured
against the bound for the capacity its own run was given.

The two fragmentation rows exist for the same reason. The solver scores `f_frag` over
the node set the optimizer was given, so the headroom run's 2,299,752 is measured
against reserved capacity and reads as *less* waste than full packing, which it is not.
Recomputed against real capacity the same plan wastes 3,265,407.50. The replication
matches the solver exactly on both runs under their own model (1,567,313.50 and
2,299,752.00), which is what establishes that the difference is the denominator and not
the arithmetic.

One further defect was observed and is not yet filed:

- **Early stop has no improvement threshold.** `stale_count` resets on any
  improvement, including 0.0003. Both runs therefore burned all 1,000 generations —
  912 s and 895 s, where the pre-fix runs stopped at generation 199 in 222 s — for
  a 0.62% gain under full packing and 0.0014% under headroom. A relative threshold
  would end the run when progress stops mattering.

Two candidate defects were investigated and dismissed:

- **The empty "Top 5" tables seen mid-session were a capture artifact.** Both runs
  at `1ab1ad7` print all five rows in each table; the earlier empty output came from
  a background-log capture that lost the lines to carriage-return overwriting.
- **The instance was never infeasible at 20% headroom**, contrary to the working
  hypothesis held for most of the session. See D-2.

## Reproducing

```bash
make bench-generate-testdata     # seeded, deterministic
make solver-irina                # full packing
make inspector-run
make bench-proof
make solver-irina-headroom-20    # 20% reserve
make inspector-run
make bench-proof-headroom-20
```

`make solver-irina` overwrites `solver/kuberina_solution.yaml`, and both verifiers
read that path, so each configuration must be verified before the next one runs.
